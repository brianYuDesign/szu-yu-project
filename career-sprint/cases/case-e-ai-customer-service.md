## 3. 結果（Result）— ★ 這一節決定履歷能不能寫數字

### 怎麼把自動回覆比例查出來

如果客服系統的對話有落庫，用下面的方式核對。**表名欄名要換成實際的。**

```sql
-- 目標：一段期間內，AI 回覆後「沒有再轉人、用戶也沒再追問同一件事」的比例
SELECT
  COUNT(*)                                          AS total_conversations,
  COUNT(*) FILTER (WHERE handed_off_to_human = false) AS resolved_by_ai,
  ROUND(
    100.0 * COUNT(*) FILTER (WHERE handed_off_to_human = false) / COUNT(*),
    1
  )                                                 AS ai_resolution_rate_pct
FROM support_conversations
WHERE created_at >= '____-__-__'
  AND created_at <  '____-__-__';
```

**三種可能的口徑，選一個並在面試時說清楚是哪一個：**

| 口徑 | 定義 | 通常數字 | 適合講的場合 |
|------|------|---------|-------------|
| **回覆覆蓋率** | AI 有給出答案（沒轉人）的比例 | 最高 | 最寬鬆，容易被追問「那答得對嗎」 |
| **自動解決率** | AI 回覆後對話就結束、沒轉人也沒重問 | 中間 | ★ 建議用這個，最經得起追問 |
| **人力節省** | 客服工時／人數的實際變化 | 最難查 | 最有商業說服力，但要有排班資料 |

> 查出數字後，履歷那條改寫成「客服提問 XX% 由 AI 直接解決、無需轉人：以 Python 建置 RAG 檢索框架…」，並在這裡註明用的是哪一種口徑。**自動解決率的講法比回覆覆蓋率強**，因為它已經隱含「答得對」。

### ⬜ 其他值得查的數字

| 指標 | 數值 | 備註 |
|------|------|------|
| 知識庫規模 | | 幾份文件、幾段切塊 —— 這個最容易查，也最能證明「真的做了」 |
| 平均回覆時間變化 | | 導入前 vs 導入後 |
| 轉人率 | | |
| 檢索準確率 | | ⬜ 當時有沒有做評測？沒有就誠實寫「沒有」 |
| 錯答事故 | | 有沒有出過事？怎麼發現的？ |

> **如果當時沒有做評測集，這是一個好的自我批評點**，而且你有現成的成長證據：
>
> 「當時沒建評測集，好不好用只能靠感覺跟客服回報。這是我後來最想補的一課 —— 離職後做的每個 RAG 專案第一件事就是先建黃金評測集，vertical-ai-kit 是 29 + 16 題、ytg 是 150 題分七層，而且把 Recall 跟 MRR 直接接進 CI，評測即回歸測試。**沒有評測集的 RAG，你根本不知道改動是變好還是變壞。**」
