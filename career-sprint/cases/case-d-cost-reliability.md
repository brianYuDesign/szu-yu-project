## ★ 這個案例的敘事主線：先建立看得見的能力，再解決看見的問題

**三段式，順序不要調換：**

```
1. 建立觀測  →  系統面接監控與告警、產品面補 GA 埋點
2. 看見問題  →  連線數逼近上限、成本結構失衡、金流對不上、告警有雜訊
```

**為什麼順序重要**：如果先講「我把連線降了 24%」，聽起來像運氣好抓到一個 bug。先講「我補上監控才看見這些問題」，整個案例就變成**主動治理**，而且解釋了為什麼這些問題會被你發現而不是別人。

> 這些問題不是有人回報給我的。是我先把觀測補上 —— 系統面接了監控工具跟連線數告警，產品面補了 GA 埋點看留存跟轉換。有數據之後才看得到問題在哪。

**技術亮點掛在第 3 段**：連線殭屍與 GA 逾時誤報，兩個看起來毫不相關的症狀，追到底是同一個機制 —— **Lambda 容器凍結不等於程序結束**。任何假設「程序會正常收尾」的東西都會出問題。

### ✅ 看見的第一件事：資料庫連線逼近上限

- 生產環境連線數峰值 **1,162**，約為 DB 上限的 **90%**

**✅ 確認：這件事發生在 SugarBee。**

實際設定（2026-07-31 從程式碼確認）：`reservedConcurrency` prod = **450**，`pool.max` prod = **20**。

### 論證：不是靠數字相減，是靠「元件失職」

理論最大連線是 450 × 20 = 9,000，而觀測值 1,162 在這個範圍內 —— 所以**不能**用「超過上限」來論證。要用更直接的角度：

> **RDS Proxy 存在的唯一意義，就是讓後端連線數遠小於前端。** 如果 Proxy 正常運作，1,162 這個數字根本不該出現 —— 它逼近 DB 上限的 90%，等於 Proxy 完全沒發揮收斂作用。而 Proxy 失效只有一個原因：連線被 pin 住了。

**這個論證比數字計算強**，因為它從元件職責出發：不是「我算出來對不上」，而是「這個元件本來就該防止這件事，它沒防住 → 它的機制被繞過了 → 去查為什麼被繞過」。

> ⚠️ **履歷原本寫「連線池上限僅 2」，與程式碼實際值（20）不符，已移除該數字。**

> ⬜ **待確認**：履歷寫「Proxy 端連線自 70–80 降至約 21」，這裡指的是
> (a) **client 到 Proxy** 的連線數 → 那麼「70–80 個 client 造成 1,162 條 DB 連線」是最漂亮的鐵證，直接證明 multiplexing 失效，講這句就夠
> (b) **Proxy 到 DB** 維持的後端連線 → 論證要改成「Proxy 自己只維持 70–80，但 DB 端總連線 1,162，代表大量連線不是經由 Proxy 管理的」

## 補充：RDS Proxy 的機制（面試被追問時的說明底稿）

**Lambda 與關聯式資料庫的結構性衝突**：Lambda 的並發模型是每個並發請求一個獨立容器，每個容器各自建立自己的 DB 連線。並發 450 就可能有 450 組連線池，而 RDS 的 `max_connections` 是固定的。並發一衝，連線先爆。

**RDS Proxy 的解法**：夾在中間維持一組到 DB 的連線，讓多個 Lambda 共用（**multiplexing**）。100 個 Lambda 進來，後端可能只用 10 條連線輪流服務。附帶好處是省掉每次 TLS 握手與認證成本，failover 也更快。

**但 multiplexing 有前提：連線必須是無狀態的。**

若某個 session 做了會殘留狀態的操作 —— session 變數、prepared statement、暫存表、`LOCK TABLES` —— Proxy 不能把這條連線交給別人（否則下一個人會讀到上一個人的狀態），於是把連線 **pin（釘住）** 給該 session 專用，直到 session 結束。

**一旦 pin，multiplexing 就失效** —— 連線退化成一對一專屬，跟沒有 Proxy 一樣。而 Lambda 容器凍結時 session 從未正常結束，那條連線就一直被釘著，只能等閒置逾時（當時 300 秒）回收。

## 2. 做法（Action）

### ✅ 診斷：RDS Proxy 殭屍連線

**根因**：pinned session 搭配過長的閒置回收時間，使凍結的 Lambda 容器留下殭屍連線。

**解法不只一道 —— 這是講這個案例時最容易漏掉的部分。**

#### 第一道：縮短殭屍連線的存活時間（基礎設施層）

RDS Proxy 閒置回收 **300 秒 → 60 秒**。治標，但立即見效。

#### 第二道：借出連線前先驗證還活著（應用層）

`models/index.js` 的 `pool.validate`，程式碼註解是你自己寫的：

> 「在連線借出前驗證是否仍有效，避免 Lambda 凍結/解凍後使用失效連線（packets out of order）」

實作上檢查 socket 是否 destroyed、readable、writable，以及有沒有 `_fatalError` / `_protocolError`。**這道防線處理的是另一個症狀**：容器解凍後，池裡那條連線可能早就被對端關掉了，直接拿來用會拿到 `packets out of order` 這種難查的錯誤。

#### 第三道：針對斷線的自動重試，而且驗證過真的攔得到

`config.retry` 設 `max: 3`，match 的 pattern 是從 **prod log 實際觀察到的訊息**回推的，不是照文件抄的：
- `Connection lost: The server closed the connection.`（連線被 RDS/Proxy 關閉，**最大宗**）
- `Client network socket disconnected before secure TLS connection was established`
- `write EPIPE`

**這裡有一個「照文件寫會踩坑」的發現**，面試時值得單獨講：

> retry-as-promised 是對 `error.toString()`（含 name + message）做比對，而 mysql2 的斷線 error 其 code（`PROTOCOL_CONNECTION_LOST`、`EPIPE`）**不會出現在 message 裡**。所以如果照直覺用 error code 當 pattern，重試永遠不會觸發 —— 而且不會報錯，只是靜靜地沒有生效。我是去看 prod log 的實際訊息文字，才回頭把 pattern 改對的。

**為什麼這段值得講**：它證明你**驗證過重試真的有攔到**，而不是設了就當作有效。設定生效與否沒有錯誤訊息會告訴你 —— 這種「靜默失效」是最難發現的一類問題。

**結果**：
- 資料庫連線數 1,162 → **883（-24%）**
- Proxy 端 client 連線 70–80 → **約 21**

> **三道防線的分工**（被問「為什麼不只調參數就好」時用）：
> 縮短回收時間**減少殭屍累積**，連線驗證**避免用到死連線**，重試**吸收仍然漏網的瞬斷**。只做第一道的話，60 秒內產生的失效連線還是會被借出去用。

### ✅ 診斷過程：四個假設，逐一排除

**這是本案例最該講細的部分。** 面試官問「你怎麼查的」時，想聽的是推理過程 —— **排除掉的錯誤假設比正確答案更有說服力**，因為那證明你不是猜對的。

你當時考慮過的四個方向：

#### 假設一：服務數量成長，連線自然變多

**為什麼合理**：serverless 架構下每個 Lambda 並發實例各自持有連線池，總連線 ≈ 並發數 × 池大小。函式越多、並發越高，連線就越多 —— 這是 Lambda + 關聯式資料庫的已知痛點。

**怎麼排除**：算了一次上界。並發有 `reservedConcurrency` 硬性上限，池大小也是固定的，兩者相乘就是理論最大值。實際連線數已經逼近甚至超過這個值 —— **如果真的是並發撐出來的，服務早該出現其他症狀**（函式被限流、延遲飆高），但都沒有。

#### 假設二：連線池上限設定過高

**為什麼合理**：連線數爆掉最常見的原因就是 pool 設太大，先查設定是正確的順序。

**怎麼排除**：查了設定，**不但沒設太高，反而是刻意設小的** —— 架構上本來就把連線共用交給 RDS Proxy，Lambda 端只留個位數的池。

> **這一步是整個診斷的轉折。** 原本要驗證「是不是設太高」，結果發現前提整個反過來：設定小到不該撐出這個量的連線。這代表**這些連線不是應用端主動持有的**，方向必須換掉 —— 從「誰開了太多」變成「誰沒有把開過的關掉」。

#### 假設三：閒置連線未關閉（連線洩漏）

**為什麼合理**：程式碼忘記 release 連線是經典 bug，而且症狀完全吻合 —— 連線只增不減。

**這個方向是對的，但層次錯了**：不是應用程式碼漏關，而是**基礎設施層的殘留**。應用沒有機會關 —— Lambda 容器被凍結時，程式碼根本沒有執行到收尾邏輯。

#### 假設四：服務重啟過程中連線增長

**為什麼合理**：重啟時舊連線還沒釋放、新連線已建立，短暫翻倍是正常現象。

**怎麼排除**：如果是重啟造成的，連線數會在重啟完成後回落。但監控上看到的是**持續累積、不回落**。

### ✅ 收斂：四個假設指向同一個結論

排除完之後，剩下的可能性只有一個形狀：

> 連線**不是應用端持有的**（池刻意設小，且 Proxy 本就負責多工），是**開了之後沒被關**（持續累積不回落），而且**不是程式碼漏關**（凍結時程式碼根本沒執行到收尾）。

符合這三個條件的只有一種情況：**連線的生命週期不由應用控制** —— 也就是 Lambda 容器凍結時，session 沒有正常結束，連線被 RDS Proxy 釘住（pinned），只能等閒置逾時回收。而當時的閒置回收設定是 **300 秒**，容器凍結／解凍頻繁時，殭屍連線就這樣堆起來。

### ⚠️ pinned session 的機制（Claude 補充，供面試用語參考）

RDS Proxy 正常情況下會讓多個 client 共用後端連線（multiplexing）。但遇到某些操作時，Proxy 無法安全共用，就會把連線「釘」給該 session 專用，直到 session 結束才釋放。常見的 pin 觸發條件：session 變數、prepared statement、暫存表、明確鎖定。

Lambda 容器凍結時 session 從未正常結束 → 連線一直被釘著 → 只能等閒置逾時。

> **核對點**
> - [ ] 你是怎麼確認「pinned」這件事的？RDS Proxy 有 `DatabaseConnectionsCurrentlySessionPinned` 這個 metric，是看這個嗎？還是從 Proxy log 看到 pin 的原因？
> - [ ] 知道是哪個操作造成 pin 嗎？（查得出來是加分題；查不出來就說「pin 的成因我沒有逐一追，直接從回收時間下手」—— 完全可以接受）
> - [ ] 為什麼是 60 秒？試過其他數字嗎？（如果是「權衡建立連線成本與殭屍累積速度」，講出這個權衡就夠）

### ⚠️ 為什麼會 pinned（Claude 補充，供你核對用語）

RDS Proxy 平常會多工共用連線，但遇到某些操作會「釘住」連線 —— 例如 session 變數、prepared statement、暫存表、鎖定。一旦被釘住，這條連線就專屬於那個 session，直到 session 結束才釋放。

Lambda 容器凍結時，session 沒有正常結束，於是連線被釘在那裡，等閒置逾時（原本 300 秒）才回收。容器凍結／解凍頻繁時，殭屍連線就會累積。

> **核對點**：你的 pinned 是什麼操作造成的？（如果查得出來，這是加分題；查不出來就講「pinned 的成因我沒有逐一追」）

### ✅ GA 逾時誤報的處理

> **補充（來自 `sugarbee/.claude/skills/ai-service/SKILL.md`）**：這件事也走過假設-推翻的過程 ——
> 原文記載「**先前 family:4/IPv6 假說已推翻**」。你一開始懷疑是網路層（IPv6 / DNS family 解析），驗證後推翻，才追到 fire-and-forget 的 promise 在 Lambda 凍結後過期。
>
> **面試講這段時要把推翻的假說講出來**：
> > GA 那批逾時告警，我一開始的假說是網路層問題，懷疑跟 IPv6 或 DNS family 解析有關。驗證之後把那個假說推翻了，真正的原因是 fire-and-forget —— handler 回應之後 promise 就被凍結，下次 invocation 解凍時計時器早就過期，所以被記成逾時，但封包其實已經送出去了。

> 這個處理方式值得展開講：**沒有直接把告警關掉，而是分級**。「關掉告警」和「區分真假告警」在面試裡是完全不同的評價。

### ✅ 成本優化：$1,200 → $600 → $400+（累計 -60%）

**這段的價值不在省了多少，在於你用了一套可複述的方法** —— 面試官聽得出「有系統地盤」和「東砍西砍」的差別。

#### 你的盤點順序（照這個講）

```
1. 現況是否合理     ← 先問「這些用量本來就該這麼多嗎」
2. 成本集中在哪     ← 找出最貴的服務與功能，先打大的
3. 流量走內網還外網  ← ★ AWS 最常見的隱形支出
4. 有無不必要的支出  ← 閒置資源、過度規格、重複呼叫
```

**第 3 步是最容易被忽略、也最容易省的一項。** 值得單獨講：

> Lambda 如果放在 VPC 裡，存取 S3 這類服務預設會繞出去走 NAT Gateway —— 而 NAT 是**按處理量計費**，資料傳輸另計。改成走 VPC Endpoint 之後，同樣的流量變成走內網、費用歸零。很多人的雲端帳單裡最大一筆其實不是運算，是這種「明明在同一朵雲裡，卻繞出去再繞回來」的流量。

#### 四個實際手段

| 手段 | 省在哪 | 附帶效果 |
|------|--------|---------|
| **改走內網／VPC Endpoint** | NAT Gateway 處理費與跨區流量費 | 延遲也降低 |
| **資源改由 S3 直出 + 引入 CDN** | Lambda 不再代理靜態資源，省運算與流量；CDN 快取後回源次數大減 | 使用者端載入更快 |
| **RDS 降規格** | 實例費用直接下降 | —— |
| **新增快取層** | 減少 DB 查詢與重複的 AI 呼叫 | 回應時間改善 |

#### ★ 一個因果關係值得特別講

**RDS 能降規格，是因為連線問題先解決了。**

殭屍連線佔著資源時，DB 的負載看起來比實際需求高，這種狀態下不敢降規格 —— 一降就怕出事。把連線收斂之後，真實負載才顯現出來，降規格才成為安全的選項。

> 這兩件事我原本是分開處理的，但實際上有先後關係：連線清乾淨之前，你看到的 DB 壓力不是真的壓力。先把假的負載去掉，才知道真正需要多大的機器。

**這段話的份量**：它顯示你不是把優化當成一張待辦清單逐項打勾，而是理解各項之間的依賴關係。

#### AI 相關的兩項（與案例 A 呼應）

- **內容審核依媒體型態分流**：圖片同步、影片非同步 —— 影片處理慢且貴，不該卡在請求路徑上
- **AI 生成結果持久化**：成本與**生成次數**綁定，而非與**瀏覽次數**綁定（詳見案例 A 的 2-4）

> ⬜ **待你補**：兩階段各自主要砍的是什麼？我的推測是第一階段（$1,200→$600）偏結構性 —— 內網化、CDN、RDS 降規格；第二階段（$600→$400）偏精細化 —— 快取與 AI 呼叫收斂。如果順序不同，講的時候要對調。

### ✅ 金流全量對帳：從一個異常追到全量驗證

**起點是主動發現，不是有人來報帳。**

```
訂閱資料出現異常
      ↓
不只修那一筆 —— 反問「還有多少筆是這樣？」
      ↓
以支付閘道 API 對 2,860 筆訂單全量對帳
      ↓
查出 5 筆「已授權未請款」+ 1 筆「交易失敗卻標記完成」
      ↓
優化反查機制 + 訂單異常處理  ← 從稽核變成機制
```

**這個路徑是本段的重點，講的時候要照這個順序。**

多數人發現一筆異常會修那一筆就結束。你做了兩件不一樣的事：

1. **把單筆異常升級成全量驗證** —— 「這一筆錯了，代表可能還有別的」。2,860 筆全查，才知道實際有 6 筆
2. **把一次性稽核變成常態能力** —— 優化反查機制、加上訂單異常處理，讓下次不用靠人工翻

**面試講法**：

> 我是先在訂閱資料上看到一些異常。修掉之後我想的是：如果這種情況會發生，那應該不只這一筆。所以我用支付閘道的 API 對全部 2,860 筆訂單做了一次全量對帳，找出 5 筆已授權但沒請款、還有 1 筆交易其實失敗卻被標記成完成 —— 那筆代表使用者沒付錢卻拿到了付費權益。查完之後我把反查機制優化掉，也補上訂單異常的處理流程，讓這件事之後是系統在管，不是靠人記得去查。

**為什麼這段在面試裡有份量**：金流出錯不是技術債，是**真實的金錢損失與信任問題**。而且「已授權未請款」這種狀態很隱蔽 —— 系統看起來一切正常，錢就是沒進來。願意去對這種帳的工程師不多。

> ⬜ **可補（有印象再說）**：那 1 筆「失敗卻標記完成」的根因是什麼？（webhook 沒收到？狀態機寫錯？重試造成的競態？）能講出根因會更完整，但講不出來也不影響 —— 重點在你做了全量驗證這件事。

---

**【前提｜約 25 秒】**

這段經驗的起點是我把觀測補上。系統面接了監控工具跟連線數告警，產品面補了 GA 埋點看留存跟轉換。這些問題不是有人回報給我的 —— 是有了數據之後才看得見。

**【診斷｜約 75 秒】**

第一個看到的是資料庫連線數逼近上限，峰值到一千一百多，大概是 DB 上限的九成。

我一開始有幾個方向：是不是服務變多所以連線自然多、是不是連線池設太大、是不是有連線洩漏、還是重啟時的暫時現象。查設定的時候我發現一件反過來的事 —— 連線池不但沒設大，**還是刻意設小的**，因為架構上是用 RDS Proxy 做連線多工，Lambda 端本來就只留很小的池。

這代表方向要換：問題不是「誰開了太多連線」，而是「誰沒把開過的關掉」。

而且 RDS Proxy 存在的意義就是讓後端連線遠小於前端。如果它正常運作，一千一百多這個數字根本不該出現 —— 等於 Proxy 完全沒發揮收斂作用。Proxy 失效只有一種可能：連線被 pin 住了。一旦連線被釘給某個 session 專用，就沒辦法共用，跟沒有 Proxy 一樣。

再往下就對上了：Lambda 容器凍結的時候，session 從來沒有正常結束，那條被釘住的連線就一直留著，只能等閒置逾時回收 —— 而當時的閒置回收設在三百秒。

**我做了三件事，不只調參數。** 第一是把 Proxy 的閒置回收從三百秒縮到六十秒，減少殭屍連線累積。第二是在應用層加上連線借出前的驗證，因為容器解凍之後，池子裡那條連線可能早就被對端關掉了，直接拿來用會出 packets out of order 這種很難查的錯。第三是針對斷線加自動重試。

重試這邊有個坑值得講：我用的套件是拿 error 的字串去比對的，但 mysql2 的斷線錯誤碼**不會出現在訊息裡**。所以照直覺用錯誤碼當條件的話，重試永遠不會觸發，而且不會報錯，只是靜靜地沒有生效。我是去看正式環境的 log、把實際的訊息文字撈出來，才把條件改對的。

最後連線數從一千一百多降到八百八，大概少了兩成四。

**【成本｜約 45 秒】**

成本這邊我的順序是：先確認現在的用量本來就該這麼多嗎、再找出成本集中在哪些服務跟功能、然後看流量是走內網還是外網、最後找有沒有不必要的支出。

第三項通常最有價值。Lambda 如果在 VPC 裡，存取 S3 這類服務預設會繞出去走 NAT Gateway，而 NAT 是按處理量計費。改成走內網之後這筆就歸零了。很多人帳單上最大一筆其實不是運算，是這種明明在同一朵雲裡卻繞出去再繞回來的流量。

其他就是靜態資源改成 S3 直出加 CDN、RDS 降規格、加快取層。分兩階段從每月一千二百美元降到四百多，大概少了六成。

**這裡有個先後關係值得說**：RDS 敢降規格是因為連線問題先解決了。殭屍連線佔著資源的時候，DB 的負載看起來比實際需求高，那種狀態下不敢降。把假的負載去掉，才知道真正需要多大的機器。

**【對帳與收斂｜約 35 秒】**

另外我在訂閱資料上看到一些異常。修掉之後我想的是，如果這種情況會發生，那應該不只這一筆 —— 所以用支付閘道的 API 對全部兩千八百六十筆訂單做了全量對帳，找出五筆已授權但沒請款、還有一筆交易其實失敗卻被標記成完成，那筆等於使用者沒付錢就拿到了付費權益。查完之後我把反查機制優化掉，也補上訂單異常的處理，讓這件事變成系統在管，不是靠人記得去查。

**回頭看，這些問題有個共同點**：serverless 的環境下，容器凍結不等於程序結束。任何假設「程序會正常收尾」的東西 —— 連線關閉、計時器、非同步請求 —— 都要重新檢查一次。
