## 一、開場

### Q. 請簡單自我介紹（90 秒）

我是 Brian，8 年軟體開發經驗，目前是 AI 工程師。

過去這一年我一個人負責一款交友配對社群 App，從需求規劃、AI 功能設計、後端服務一路做到 iOS 上架。AI 的部分我做了四個功能——自介生成、配對建議、破冰話題、聊天教練，它們不是各自獨立的實驗，是沿著使用者旅程的四個斷點，而且我刻意讓 AI 越往後介入越少。建檔階段可以幫他寫，但聊天不行，AI 完全介入的話交友就沒意義了。這幾個功能是訂閱方案的付費內容，所以品質直接關係到續訂。

除了做功能，我也花不少時間在系統的成本跟穩定度上。查過一個資料庫連線逼近上限的問題，追到是 Lambda 容器凍結留下的殭屍連線，處理完降了兩成四；雲端支出從每月一千二百美元降到四百多；首頁的 FCP 從 10 秒壓到 1.4 秒。

我接下來想找的是能把一條 AI 產品線持續做深的位置。先前帶過 11 人團隊、也建過 review 跟 release 的流程，那段經驗我覺得很有價值；接下來我想把重心放在技術深度上，如果角色需要主導技術方向或帶一兩個人，我也做得來。

> 結尾不要講「走獨立 IC」，會自己篩掉 Tech Lead / Staff 職缺。
> 禁用字：救火、什麼都做、都有碰、比較雜。

## 二、AI 產品（主打題）

### Q. 講一個你把 AI 接進產品的例子 ★

起點不是「我們遇到什麼問題所以要用 AI」，是我先盤點既有功能，一個一個評估：導入 AI 這個功能會變好嗎、代價是什麼，然後才決定哪些做、哪些不做。

最後做了四個功能，是使用者旅程上的四個斷點：建檔時使用者填的資料很短、自介常常空著，所以做**自介生成**；配對時不知道為什麼該跟這個人聊，所以做**配對建議**；開場是最痛的一段，男女都不主動、第一句常常就是「約嗎」，所以做**破冰話題**；聊起來卡住了，才有**聊天教練**。

這裡有一個刻意的設計：**AI 的介入程度隨旅程遞減**。建檔階段我願意讓 AI 幫他寫，因為那是一次性的門面；但聊天不行，AI 如果完全介入，交友這件事就失去意義了。所以越往後 AI 越退居輔助，最後只在使用者主動求助時才出現。

技術上我最在意成本跟可靠性。生成結果一律存資料庫，同一份內容不會被生第二次，費用是跟生成次數綁定不是跟瀏覽次數綁定，上面再加記憶體與 Redis 的雙層快取。可靠性的部分是三層合併式降級，模型異常時使用者無感。

> 重點放在兩件事：**起源是盤點不是痛點**、**主動決定不做什麼**。這比任何技術細節都重要。

### Q. 這些 AI 功能有人用嗎？怎麼證明有價值？

這幾個 AI 功能不是免費附加的，是訂閱方案的核心功能之一——使用者是為了這些功能付費，從 log 看得到實際使用量。所以品質不只是體驗問題，是付費用戶會不會續訂的問題。訂閱方案裡還有其他商用功能，所以 AI 是訂閱權益之一，不是唯一賣點。

### Q. 為什麼選 Claude，不選其他模型？

當時是一人開發、要快速驗證 AI 對產品的實際加成，所以直接選了公開評比上表現穩定的 Claude，沒有做內部橫評。我知道其他選項的取捨在哪——成本、推理效率，或是自建本地模型換取資料不出去。以當時的階段來說，先把功能驗證出來比選型精準更重要；如果現在要重做，我會先用一組 eval set 對兩三個模型跑同一批輸入再決定。

### Q. 你怎麼確保模型輸出的品質？★★（目前最弱）

我目前做的主要是幾層防護。輸出用 JSON 格式約束，系統提示明寫「請只輸出 JSON，格式必須是 `{"suggestions":[...]}`」；輸入的使用者資料會去識別化、用分隔標記包起來，並在系統提示裡宣告為不可信資料。生成出來之後還有一層正則過濾，四組 pattern 擋掉索取聯絡方式、探問收入年紀、過度親暱、電話號碼這幾類——因為第一句話踩到這些使用者體感很差，而模型偶爾就是會越界。另外降級是合併式的：AI 產出多少用多少，不足的用模板補滿，所以使用者永遠拿到三則。

但我要誠實說，這些是「防止最差」，不是「確保夠好」。我們的開發規範裡有要求每個 AI 功能建 50 到 200 筆的評測集、改 prompt 必須跑過評測才能合併，但那部分我還在建。我現在的做法是把「好」拆成四個維度：安全性、相關性、可回覆性、語言自然度，安全性是硬性的，其他三個各 0 到 2 分。

### Q. 怎麼防 prompt injection？

輸入面：使用者內容去識別化、用分隔標記包裹、在系統提示裡宣告為不可信資料。輸出面：分類與審核類一律用 structured outputs，固定枚舉加信心分數，把輸出面封死；生成類再過一層正則過濾。另外生成物一律是草稿加使用者確認，不自動代發。

### Q. 模型出錯或逾時的時候會怎樣？

我設計的是三層：AI 生成、依 profile 的模板、通用文案，三層**合併**之後去重取前三則——不是「AI 失敗就整批換模板」。因為如果模型只回了一則、或有兩則被過濾掉，二選一的降級會把 AI 的結果整批丟掉。合併的話 AI 產出多少就用多少，不足才補模板，使用者永遠拿到三則，而且是盡可能高品質的那三則。開場白還有 36 字長度上限，去重是用 lowercase 當 key。

逾時我一開始設 4.5 秒，後來 premium 走 Sonnet 之後，生產環境的 P95 超過這個數，就會 axios timeout、AI 建議變空、前端報 `chatCoachAdviceFailed`。所以改成 8 秒——上限是 Lambda 的 60 秒預算，下限不能低於 Sonnet 的 P95。同時把聊天教練的逾時也對齊，避免兩個服務行為不一致。

> 加分點：逾時參數是**依實測數據調的**，而且追出了「逾時太短 → 空結果 → 前端錯誤」這條完整因果鏈。

### Q. 快取怎麼設計的？

雙層。第一層是 Lambda 容器內的記憶體 Map，容器 warm 的期間同一個 key 連 Redis 都不用打，省一次網路往返；第二層是 Redis，TTL 一小時。key 長這樣：`icebreaker:v1:{currentUserId}:{targetUserId}:{tier}:{style}`。

三個設計是刻意的：key 帶 `v1` 版本前綴，prompt 或格式改版時換成 `v2` 就整批失效，不用去掃 Redis 刪 key；`tier` 跟 `style` 納入 key，不同語氣的開場白各自快取不互相覆蓋；兩個 userId **不排序**，因為破冰話題是「我要對他說的第一句話」，方向本來就有意義，A→B 和 B→A 本來就該是不同內容。另外有 `forceRefresh` 參數讓使用者強制重生成。

### Q. LLM 的成本你怎麼控？

三個層次。第一，生成結果一律落地——每一次生成都是實際成本，同一份自介不會因為使用者重開編輯頁就再打一次模型，只有主動要求重新生成才會有新呼叫。這樣費用跟生成次數綁定，不跟瀏覽次數綁定。

第二，LLM 有一個一般 API 沒有的問題：**重複請求不只是浪費資源，是直接產生費用**。使用者連點幾下或前端重試，那時候快取跟 DB 都還是空的，就會各自呼叫一次模型付好幾次錢。所以生成前先上一把短期分散式鎖，同一筆同時間只允許一個請求真的去打模型，其他的等結果，等不到就走預設文案。鎖一定要設 TTL，而且 TTL 要大於模型逾時上限，否則鎖先過期又會多打一次。

第三是規範層的護欄：非即時任務走 Batch API 省一半、系統提示做 prompt caching、token 用量落庫進 CMS 成本看板、每個功能設日預算熔斷跟 per-user rate limit，防止被當免費 ChatGPT 用。模型也分層，審核初篩用 Haiku、生成類用 Sonnet、低頻深度分析才用 Opus。開發環境沒有 API key 時完全不呼叫，直接走模板，不會產生費用。

### Q. 為什麼不做預生成？

純粹看效率跟成本，預生成一定最好——LLM 有 API 往返時間，請求本身就有延遲。但這幾個是附加功能，不是產品主推。在一人開發、要先驗證 AI 對產品有沒有實際加成的階段，我選擇先用最直接的方式實作，把架構優化留到功能被驗證有價值之後。

優化路徑我很清楚：判準是使用者「主動按下按鈕」的就即時，他預期會等；使用者「被動看到」的就預生成，他不該等。所以破冰話題應該在配對成立時非同步預生成 3–5 則存起來，點進聊天室零等待，成本也變可預測——跟配對數綁定，不隨滑動次數爆炸。配對建議隨配對池更新批次生成。自介生成維持即時就好，使用者按下「幫我寫」有明確預期。聊天教練本質上無法預生成，必須依當下對話，要省成本只能裁切 context。

### Q. 四個功能裡哪個最難？

最難的是自介生成。使用者輸入的資料很短，可能就三四個興趣標籤，但輸出要是一段讀起來像他本人的自介。**資訊量最少卻要最個人化**，模型很容易寫成那種放諸四海皆準的句子——而那正好是自介最失敗的樣子，每個人的自介都長一樣。破冰話題反而簡單，只要不尷尬能接話就成立，使用者不喜歡還能換一則。

### Q. 你一個人做，怎麼確保架構品質？

三件事：1,066 項自動化測試（AI service 有單元測試，模型呼叫用 mock 掉）、型別約束、以及把規範寫成文件。我們有一份 AI 開發規範，規定所有 LLM 呼叫的架構位置、成本護欄、輸出安全跟政策紅線——例如一律用官方 SDK 不用 LangChain、prompt 目錄要版本化、改 prompt 算正式變更要 review、LLM 呼叫必須 await 禁止 fire-and-forget、AI 永不阻塞關鍵路徑，付款發訊配對在 AI 失敗時照常運作。

### Q. 你做過 AI agent 嗎？

做過一個 POC 的分析 agent，讓後台可以用自然語言查資料做用戶分析。那個階段我是給它特定資料表的查詢權限，像訂單紀錄；用戶紀錄這種敏感資料我沒開。

後來我在自己的專案裡再做一次類似的東西，才意識到更好的做法是**預先定義好幾個查詢讓模型選參數**，而不是給它表的權限。三個理由：模型不可能生出你沒預期的查詢，行為空間是收斂的；每個查詢的效能可以事先確認，不會被生出全表掃描；稽核也簡單，log 記的是「呼叫了哪個查詢、帶什麼參數」，不用去 parse SQL。

## 三、除錯與可靠性（主打題）

### Q. 講一個你查過最難的問題 ★

先講前提：這個問題不是有人回報給我的。是我先把觀測補上——系統面接了監控工具跟連線數告警，產品面補了 GA 埋點看留存跟轉換。有了數據之後才看得見。

第一個看到的是資料庫連線數逼近上限，峰值一千一百多，大概是 DB 上限的九成。

我一開始有四個方向：服務變多所以連線自然多、連線池設太大、連線洩漏、還是重啟時的暫時現象。查設定的時候發現一件反過來的事——**連線池不但沒設大，還是刻意設小的**，因為架構上是用 RDS Proxy 做連線多工，Lambda 端本來就只留很小的池（prod 是 `reservedConcurrency` 450、`pool.max` 20）。

這代表方向要換：問題不是「誰開了太多連線」，而是「誰沒把開過的關掉」。

而且 RDS Proxy 存在的意義就是讓後端連線遠小於前端。如果它正常運作，一千一百多這個數字根本不該出現——等於 Proxy 完全沒發揮收斂作用。Proxy 失效只有一種可能：連線被 pin 住了。一旦連線被釘給某個 session 專用，就沒辦法共用，跟沒有 Proxy 一樣。

再往下就對上了：Lambda 容器凍結的時候 session 從來沒有正常結束，那條被釘住的連線就一直留著，只能等閒置逾時回收——而當時設在三百秒。

**我做了三件事，不只調參數。** 第一，Proxy 閒置回收從 300 秒縮到 60 秒，減少殭屍累積。第二，應用層加上連線借出前的驗證，檢查 socket 是不是 destroyed、readable、writable，因為容器解凍後池裡那條連線可能早就被對端關掉，直接拿來用會出 `packets out of order` 這種很難查的錯。第三，針對斷線加自動重試，max 3 次。

結果連線數從 1,162 降到 883，少了兩成四；Proxy 端 client 連線從 70–80 降到約 21。

### Q. 為什麼不只調參數就好？三道防線的分工是什麼？

縮短回收時間**減少殭屍累積**，連線驗證**避免用到死連線**，重試**吸收仍然漏網的瞬斷**。只做第一道的話，60 秒內產生的失效連線還是會被借出去用。

### Q. 重試設定有什麼坑嗎？

有，而且是「靜默失效」那種最難發現的。retry-as-promised 是對 `error.toString()`（含 name + message）做比對，而 mysql2 的斷線 error 其 code——`PROTOCOL_CONNECTION_LOST`、`EPIPE`——**不會出現在 message 裡**。所以如果照直覺用 error code 當 pattern，重試永遠不會觸發，而且不會報錯，只是靜靜地沒有生效。

我是去看 prod log 的實際訊息文字，才回頭把 pattern 改對的。實際攔的是 `Connection lost: The server closed the connection.`（最大宗）、`Client network socket disconnected before secure TLS connection was established`、`write EPIPE` 這幾條。

> 這段的價值：證明你**驗證過重試真的有攔到**，而不是設了就當作有效。

### Q. RDS Proxy 是什麼？為什麼會 pinned？（追問底稿）

Lambda 跟關聯式資料庫有結構性衝突：Lambda 每個並發請求一個獨立容器，每個容器各自建連線池，並發 450 就可能有 450 組池，而 RDS 的 `max_connections` 是固定的，並發一衝連線先爆。

RDS Proxy 的解法是夾在中間維持一組到 DB 的連線讓多個 Lambda 共用，也就是 multiplexing。100 個 Lambda 進來，後端可能只用 10 條連線輪流服務，附帶好處是省掉每次 TLS 握手跟認證成本，failover 也更快。

但 multiplexing 有前提：連線必須是無狀態的。如果某個 session 做了會殘留狀態的操作——session 變數、prepared statement、暫存表、`LOCK TABLES`——Proxy 不能把這條連線交給別人，否則下一個人會讀到上一個人的狀態，於是把連線 pin 給該 session 專用，直到 session 結束。一旦 pin，multiplexing 就失效，退化成一對一。而 Lambda 容器凍結時 session 從未正常結束，那條連線就一直被釘著。

### Q. GA 那批逾時告警是怎麼回事？

我一開始的假說是網路層問題，懷疑跟 IPv6 或 DNS family 解析有關。驗證之後把那個假說推翻了，真正的原因是 fire-and-forget——handler 回應之後 promise 就被凍結，下次 invocation 解凍時計時器早就過期，所以被記成逾時，但封包其實已經送出去了。

處理方式不是把告警關掉，是**依錯誤型態分級記錄**，消除假警報的同時保留真實故障的可見性。

### Q. 這件事你學到什麼？（收尾必講）

這件事之後我對 serverless 的心智模型調整了：**容器凍結不等於程序結束**。任何假設「程序會正常收尾」的東西——連線關閉、計時器、非同步請求——都要重新檢查一次。連線殭屍跟 GA 誤報兩個看起來毫不相關的症狀，追到底是同一個底層行為。所以後來我們的規範直接寫死：LLM 呼叫必須 await，禁止 fire-and-forget，需要背景化就走 SQS。

## 四、成本

### Q. 你怎麼做成本優化的？

我的盤點順序是四步：先問「這些用量本來就該這麼多嗎」，再找出成本集中在哪些服務跟功能先打大的，然後看流量是走內網還是外網，最後找有沒有不必要的支出。

第三步通常最有價值。Lambda 如果放在 VPC 裡，存取 S3 這類服務預設會繞出去走 NAT Gateway，而 NAT 是**按處理量計費**，資料傳輸另計。改成走 VPC Endpoint 之後，同樣的流量變成走內網、費用歸零。很多人的雲端帳單裡最大一筆其實不是運算，是這種「明明在同一朵雲裡，卻繞出去再繞回來」的流量。

其他手段是靜態資源改成 S3 直出加 CDN，Lambda 不再代理靜態資源、省運算跟流量，CDN 快取後回源次數大減；RDS 降規格；加快取層。分兩階段從每月 1,200 美元降到 400 多，少了六成。

### Q.（追問）RDS 為什麼敢降規格？

**因為連線問題先解決了。** 殭屍連線佔著資源的時候，DB 的負載看起來比實際需求高，那種狀態下不敢降，一降就怕出事。把假的負載去掉，真實負載才顯現出來，降規格才成為安全的選項。這兩件事我原本是分開處理的，但實際上有先後關係。

## 五、金流與數據

### Q. 講一個你主動發現的問題

我先在訂閱資料上看到一些異常。修掉之後我想的是：如果這種情況會發生，那應該不只這一筆。所以我用支付閘道的 API 對全部 **2,860 筆訂單**做了一次全量對帳，找出 **5 筆已授權但沒請款**、還有 **1 筆交易其實失敗卻被標記成完成**——那筆代表使用者沒付錢卻拿到了付費權益。

查完之後我把反查機制優化掉，也補上訂單異常的處理流程，讓這件事之後是系統在管，不是靠人記得去查。

> 重點在兩個動作：把單筆異常升級成全量驗證、把一次性稽核變成常態能力。

### Q. 營收成長 81% 有多少是你的功勞？⚠️

那段期間的成長不會是單一原因。我負責的是金流這條——自動續訂、扣款失敗處理，還有把前端取消沒回寫的缺口補起來，用多訊號交叉查詢還原真實的退訂數，才分得出來哪些是真的退訂、哪些只是換卡導致扣款中斷。後者是可以挽回的，挽回流程就是從這裡來的。行銷跟產品那邊同期也有動作，我沒辦法拆出精確的歸因。

> 不獨攬也不過度謙虛，顯示你懂得區分「相關」與「因果」。

## 六、團隊與職涯

### Q. 你怎麼影響團隊？

那個團隊當時有三個症狀：上版頻頻出包、程式碼耦合過高、寫法過於分散。更根本的是**團隊沒有共同的品質標準**，每個人對「做完了」的定義不一樣。還有一個是端到端的呼叫沒有被有效追蹤，出事時連壞在哪一段都要猜。

我在設計、實作、上線各放一個檢查點：設計前的 design review 解決 exception case 沒被充分探討、實作中的 code review 收斂寫法與耦合、上線前的 release checklist 解決出包。這三個不是分開想出來的，是對著問題發生的時間點放的——出包最貴的地方在於發現得太晚，所以讓問題盡量在便宜的階段就被發現。

但**關鍵不是流程本身**。我不是訂一套規則叫大家照做，那樣的東西通常只會變成一份沒人看的文件，尤其在大家對品質標準本來就沒共識的時候。我的做法是漸進導入，而且是跟成員一起討論出標準——討論的問題不是「該遵守什麼規範」，而是「怎麼在設計階段就避免掉這類問題」「出事的時候怎麼最快找到是哪裡壞了」。這兩個問題對每個工程師都是切身的，討論起來大家願意投入，訂出來的東西也就自然會被用。

> 措辭紅線：**不要講「成員責任感低」**。講「團隊當時沒有共同的品質標準」——焦點從「人不夠好」移到「制度不存在」，而後者剛好是你解決的東西。

### Q.（追問）那些流程後來還在用嗎？

我離開之後就沒有再追蹤了，所以不敢說它延續了多久。當時的效果是上版的問題確實有減少，設計階段的討論也比以前完整。

> 誠實在這題反而加分。說「一直沿用到現在」但答不出細節，傷更大。

### Q. 你想帶人嗎？

我帶過 11 人團隊，也建過 design review、code review 跟 release 流程，那段經驗我覺得很有價值。接下來我想把重心放在技術做深，特別是 AI 這塊。如果角色需要帶一兩個人或主導技術方向，我做得來也願意；但我不想把時間全部放在管理上。

> 兩面都不關門。措辭與自我介紹結尾保持同一套。

### Q. 為什麼想離開現在的工作？

我想找一個能把一條 AI 產品線持續做深的環境。現在這邊我做的範圍很廣——AI 功能、金流、效能、成本都碰，這一年學到很多。但有些我想深入的東西還沒機會做，像是模型評估體系、提示設計的版本管理、AI 的指標治理，這些在一人開發、快速迭代的節奏下比較難鋪開。我想找一個有這個需求、也給得起這個空間的團隊。

> 往前講不往後講。不講前公司壞話、不講救火。

### Q. 你最大的弱點是什麼？

我的 AI 經驗偏應用整合——把模型接進產品、讓它穩定跑、控制成本，這塊我很熟。但更偏研究的部分，像是模型微調、embedding 檢索的調校、或是長期負責一套評估體系，我實際做的還不夠深。這也是我最近在補的方向，我現在在幫破冰話題那個功能建評測集，先從「怎麼定義好」開始。

> 用真的弱點，而且答案本身證明你有在補。

### Q. 你對我們的產品有什麼想法？

⬜ 沒有通用答案，投遞前針對每家準備。花 20 分鐘用他們的產品，找一個**具體的**觀察（不是「介面很簡潔」）。最好能連到你的經驗，例如「你們的 X 功能看起來是 AI 生成的，我猜背後可能是 Y 做法，因為我做過類似的」。
