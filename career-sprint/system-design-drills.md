## 為什麼 LLM 系統設計跟傳統系統設計不一樣

傳統系統設計的估算是 QPS、儲存、頻寬。LLM 系統設計多了四件事，而**這四件正是
面試官用來分辨「做過」與「讀過」的地方**：

| 多出來的維度 | 傳統系統設計沒有的原因 |
|---|---|
| **Token 經濟學** | 每個請求的成本不是固定的，取決於 prompt 長度與輸出長度 |
| **GPU 容量規劃** | 地端不是加機器就線性擴充，飽和點低得反直覺 |
| **品質治理** | 「正確」不是二元的，需要一整套指標與門檻 |
| **權限邊界** | 檢索層就要過濾，不能生成後才擋 |

只講傳統那三樣會被看出來沒做過。只講「用 GPT-4 加 RAG」也會。

## 10 分鐘的骨架

| 時間 | 段落 | 這一段真正在證明什麼 |
|---|---|---|
| 0:00–2:00 | **需求澄清** | 你知道哪些問題會改變設計，哪些不會 |
| 2:00–4:00 | **容量與 token 經濟學** | 你算過真實系統的帳（多數人跳過這段） |
| 4:00–7:00 | **架構主圖** | 你能把元件之間的關係畫清楚 |
| 7:00–9:00 | **深挖一個元件** | 你有深度，不只是會排方塊 |
| 9:00–10:00 | **取捨與失敗模式** | 你知道自己選的東西什麼時候會壞 |

**最後一段千萬不要被時間吃掉。** 那是資深與否最明顯的分界，
而它剛好排在最容易被前面超時擠掉的位置。畫圖時就要留這一分鐘。

## 估算工具箱（背下來，現場要能口算）

### Token 經濟學

一次 RAG 問答的 token 結構（實測，retail pack）：

```
系統提示 + 5 段參考資料 + 問句  ≈  400–1,200 input tokens
答案（三段以內）                ≈  80–120 output tokens
```

**一條 pipeline 有多個 LLM 呼叫點，別只算生成那一次。**
重排序、稽核、追問改寫各自都要付錢，而重排序是頻率最高的。

月成本口算：

```
月成本 ≈ 月問答量 × (input × 輸入單價 + output × 輸出單價) / 1,000,000 × 呼叫點數
```

現場範例（Haiku 等級 $1 / $5 per MTok，每月 10 萬次問答，兩個呼叫點）：

```
輸入：100,000 × 1,000 × 2 = 2 億 tokens → $200
輸出：100,000 ×   100 × 2 = 2 千萬 tokens → $100
月成本 ≈ $300
```

**接著馬上講快取。** 這是把成本題變成設計題的轉折：

> 「這個數字的前提是每一次都真的打模型。實測快取命中是 1.1 秒、未命中 75 秒，
> 差 68 倍。所以我要問客戶的不是『你們有幾個人』，而是『你們的問題重複率多高』——
> 後者對成本與硬體的影響大得多。」

### GPU 容量規劃

**實測基準（自己量的，要主動說明環境）**：

```
qwen2.5:14b + bge-m3，Apple Silicon Mac，Ollama 預設設定
飽和點：併發 2–4
天花板：約 1.3 問答 / 分鐘 = 80 問答 / 小時 / 台
併發 8 比併發 4 更慢（負效果，不是零效果）
```

現場算法：

```
需要的機器數 ≈ 尖峰時段問答量 / 小時 ÷ (單台每小時上限 × (1 − 快取命中率))
```

**兩句一定要說的話**：

1. 「絕對數字不能外推到客戶機房——這是 Mac 統一記憶體不是 A100。
   **可外推的是形狀**：地端 LLM 的飽和點很低，而且過了飽和點加併發是負效果。」
2. 「用 web 服務的心智模型做 LLM 容量規劃會嚴重高估。一般服務調到併發數十上百
   是常態，這裡是個位數。」

### 延遲預算

```
快取命中          ≈ 1.1 秒   （只剩 embedding + 檢索）
地端 14b 未命中   p50 7.5 秒 / p95 73.8 秒 ← 差 10 倍
地端 27b          單題約 400 秒 → 互動場景直接排除
```

**p50 與 p95 差 10 倍這件事本身要拿出來講**：成因是模型在記憶體壓力下被換進換出。
結論是「地端部署要嘛把模型釘在記憶體裡，要嘛把冷啟動算進 SLA」。

## 六題

### 第 1 題：設計一個企業內部 AI 助理

> 你主管的原題。**先練這題，練到不用想。**

**這題在考什麼**：範圍界定的能力。「企業內部 AI 助理」是一個沒有邊界的題目，
直接開始畫架構的人會輸在第一分鐘。

**澄清必問的三個問題**（每個都會改變設計）：

1. **知識來源是什麼？** 內部 wiki／SOP／工單系統／程式碼？
   → 決定切塊策略、要不要多資料源、權限模型
2. **誰會用、答錯的代價是什麼？** HR 問假期 vs 工程師問線上事故處理程序
   → 決定煞車放在哪、要不要人工複核
3. **資料能不能出公司？** → 決定雲端 / 地端，而這會改變整張成本與容量的算法

**主圖必備元件**：入口（Slack / 內部 portal）→ 權限過濾 → RAG pipeline（三張圖的第一張）
→ 兩道煞車 → 觀測與回饋迴路。旁邊掛一條「知識庫更新」的離線流程。

**常見陷阱**：
- 只畫 query 路徑，忘了畫**文件更新怎麼進系統**。企業知識庫每天都在變。
- 把權限做在生成後（「叫模型不要說」）——**必須做在檢索層**，
  否則機密內容已經進了 prompt，任何 prompt injection 都可能撈出來。
- 沒有回饋迴路。線上問答紀錄是下一輪評測集最好的來源。

**可以搬出來的數字**：快取 68 倍、地端容量 80 問答/小時/台、兩道煞車的設計理由。

### 第 2 題：AI 客服降本 50%，品質不能掉

**這題在考什麼**：你會不會把「降本」拆成可以動的槓桿，而不是直接說「換小模型」。

**四個槓桿，照投報率排序**：

| 槓桿 | 效果 | 風險 |
|---|---|---|
| 快取 | 實測 68 倍延遲差，成本同比例 | 答案永遠一樣（客服場景是優點） |
| 依任務路由 | 重排序換小模型，它是頻率最高的呼叫點 | 排序品質可能掉，要量 |
| 縮短 prompt | 參考資料段數、單段截斷長度 | 直接影響 groundedness |
| 換小模型做生成 | 最大但最危險 | 要有評測集才敢動 |

**這題的正確答案結構**：先講「我需要先知道錢花在哪」——沒有 per-呼叫點的成本
拆解就談降本是瞎猜。然後照上表由低風險往高風險走，**每一步都要有 A/B 的門檻**。

**陷阱**：「品質不能掉」必須被定義成數字，否則這題無解。
主動說：「我會先建一組評測集與六個指標三層門檻，降本的每一步都跑一次，
沒過門檻就退回。」

---

### 第 3 題：多租戶 RAG SaaS（資料隔離）

**這題在考什麼**：安全邊界的直覺。

**三層隔離，要能講出各自擋什麼**：

1. **儲存層**：`tenant_id` 進每一張表、每一個索引。RLS 或強制帶條件的 DAO。
2. **檢索層**：向量檢索的 filter 一定要在 SQL 裡，不能在應用層過濾結果——
   後者代表別的租戶的向量已經被算過相似度了。
3. **快取層**：**key 一定要含 tenant_id**。這是最容易漏的一個，
   而漏了的後果是 A 租戶問一次，B 租戶拿到 A 的答案。

**加分**：pgvector 的 HNSW 在多租戶過濾下會有 post-filter 漏召回的問題，
要開 `iterative_scan`。這是實際踩過才知道的細節。

**陷阱**：只講資料庫隔離，忘了快取、忘了 log（`query_logs` 也要帶 tenant_id 並做 PII 遮蔽）。

---

### 第 4 題：文件問答 + 細粒度權限

**這題在考什麼**：能不能識破「生成後過濾」這個錯誤答案。

**核心論點一句話**：

> 權限必須在**檢索層**過濾。生成後才擋，代表機密內容已經進了 prompt，
> 而 prompt 是可以被誘導吐出來的。

**設計**：文件 ingest 時把 ACL 一起寫進 chunk metadata → 檢索的 SQL 帶使用者的
group 條件 → 引用回傳時再驗一次（防止 ACL 在檢索後被改）。

**難點要主動提**：ACL 變更之後，快取裡的舊答案怎麼辦？
答案是快取 key 要含權限指紋，或權限變更時整代失效（版本前綴就是為這種事準備的）。

**陷阱**：說「用不同的 index 分開存」——文件數多、群組組合爆炸時不可行。

---

### 第 5 題：地端 GPU 叢集容量規劃

**這題在考什麼**：你有沒有真的量過。這題最容易當場現形。

**照這個順序講**：

1. **先問尖峰**，不是平均。平均會讓你少買一半的卡。
2. **拿出單台實測**：14b 飽和點併發 2–4、天花板 80 問答/小時。
   主動說環境與限制（Mac 不是 A100，樣本只有 4 個所以 p95 等於最大值）。
3. **算快取後的有效容量**。這是把答案從「買 N 台」變成「先問重複率」的轉折。
4. **講模型尺寸的取捨**：27b 單題 400 秒，互動場景直接排除——
   **這是依據耗時排除，不是依據品質**，要說清楚差別。
5. **留緩衝**：模型冷載入、記憶體壓力下的驅逐都會製造 10 倍的延遲變異。

**陷阱**：線性外推。併發 8 比併發 4 慢是實測到的——過了飽和點加併發是負效果。

---

### 第 6 題：模型路由平台

> 這題你有現成的實作，是最容易講深的一題。

**這題在考什麼**：抽象能力，以及你知不知道抽象的代價。

**主圖**：三張圖的第二張，直接用。

**四個要講到的點**：
1. **依任務路由而非依模型路由**——同一條 pipeline 上四個呼叫點性質完全不同。
2. **錯誤分三類而不是兩類**（RETRY / FAILOVER / FATAL），並講 401 只打一次的實測。
3. **斷路器粒度**——講那個「一個不存在的模型害死一個好模型」的 bug。
   這是整場最有說服力的段落，因為它不是讀來的。
4. **快取放在韌性層外面**，並講清楚為什麼順序是設計本身。

**陷阱**：講成「就是一個 LiteLLM」。要能說出你為什麼不用現成 gateway：
多數 gateway 按 model 路由不按 task，而且交付到客戶機房時每一層都要能自己解釋。
