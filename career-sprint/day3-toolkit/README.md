### 第二步：建評測集

```bash
cd ~/Project/feeling-bank/bound/bound-front-backend
cp <此目錄>/eval-dataset-template.jsonl ./eval-dataset.jsonl
cp <此目錄>/run-eval.js ./run-eval.js

node run-eval.js --limit 3     # 先跑 3 筆確認流程通
node run-eval.js               # 跑全部
```

範本有 17 筆，其中 **11 筆是刁鑽案例**（資訊極少 3、髒資料 3、越獄嘗試 3、敏感情境 2）—— 比例偏高是因為範本刻意示範各種刁鑽類型。

**擴充到 40 筆時，要多補一般案例**，讓刁鑽比例回到三成左右。全是刁鑽案例的評測集會失真：分數低不代表模型差，只代表你專挑難的。

SKILL.md 規範寫 50–200 筆，但**能跑起來的 40 筆勝過永遠沒建完的 200 筆**。

### 第三步：人工標註

腳本會自動判定**安全性**（重用 service 的正則）並標記每則的**來源**（AI 或模板）。人工只需填三個維度：

- `relevance`（相關性）0–2
- `replyability`（可回覆性）0–2
- `naturalness`（自然度）0–2

判準見 `eval-rubric.md`。**先標 20 筆校準，再回頭重標前 10 筆** —— 標到第 10 筆時你對分界線的認知會比第 1 筆清楚得多。

## `run-eval.js` 的三個設計決定

**1. 呼叫 service 而非直接打 API**

測的是完整管線（fallback 合併、正則過濾、長度限制、模型分層），不是裸 prompt。裸 prompt 測出來的分數在生產環境沒有代表性。

**2. `forceRefresh: true`**

跳過雙層快取。否則第二次跑會拿到快取結果，評測完全失效 —— 這是最容易踩的坑。

**3. 自動標記 AI / 模板來源**

做法是再跑一次不帶 `ANTHROPIC_API_KEY` 的版本取得純模板輸出，比對後就知道哪幾則來自 AI。

> **`aiCount` 這個指標是你的架構特有的。** 因為 fallback 是「合併」不是「取代」，三則裡可能混著 AI 與模板。如果 AI 只貢獻 1 則，即使總分不差，也代表模型或 prompt 退化了 —— **這個訊號在只看總分時會被模板的分數蓋掉**。
>
> 面試講這點很加分：它顯示你不是套用通用評測框架，而是針對自己的架構設計了對應的觀測指標。
