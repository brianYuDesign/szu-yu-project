# Day 2 — 兩個代表案例（4h）

**要解決的缺口**：履歷只有 bullet，面試時撐不起深度追問
**產出**：兩份 STAR 完整版 + 各一張架構／流程圖

Cake 指定的兩個案例：**交友配對（Claude）** 與 **內容安全（Rekognition）**。這兩個剛好一個是「模型能力做成產品功能」、一個是「AI 系統的可靠性與風險」——正好覆蓋 AI 應用工程師面試的兩大題型。

---

## 為什麼要寫成完整文件，而不只是 bullet

面試官看到「運用 Claude 提供配對建議」時，會問的是：

- 你怎麼知道配對建議是好的？（→ 評估）
- prompt 改了以後怎麼確認沒有變差？（→ 迴歸測試）
- 一天呼叫幾次？成本多少？延遲多少？（→ 成本與效能）
- 模型回傳爛結果時使用者看到什麼？（→ 降級策略）

這四個問題答不出來，就是 Cake 說的「純 AI 深度還可以再往前推」。Day 2 先把**事實**寫完整，Day 3 補**治理**。

---

## 案例 A：Claude 驅動的配對與對話輔助（2h）

用這個結構寫，每段限 150 字以內：

### 1. 問題（Situation / Task）
- 交友平台的核心痛點是什麼？（配對後不聊天？破冰困難？簡介寫不出來？）
- 為什麼是 LLM 而不是規則或推薦模型？
- 當時的限制是什麼？（一人開發、時間、成本、iOS 審核）

### 2. 做法（Action）—— 這段要有技術密度
- **功能拆解**：配對建議 / 聊天教練 / 破冰話題 / 個人簡介生成，四個各自的輸入與輸出是什麼
- **提示設計**：system prompt 怎麼組？使用者資料怎麼進 context？有沒有做結構化輸出（JSON schema / tool use）？
- **服務整合**：NestJS 這一層怎麼包？同步還非同步？失敗重試？快取哪些結果（Redis）？
- **成本控制**：哪些請求可以不打模型？有沒有做結果快取或短路？
- **降級**：模型逾時或回傳不合格時，使用者看到什麼？

### 3. 結果（Result）—— 必須有數字
硬數字優先用你已經有的：**180+ API、1,066 項自動化測試**。
再補上任何你手上有的：日活、配對數、AI 功能使用率、平均回應時間、單次呼叫成本、iOS 上架時間。

> **沒有產品數據也沒關係**——工程數字（延遲、成本、測試覆蓋、錯誤率）同樣有說服力，而且更可信。不要編造成長率。

### 4. 一張圖
畫使用者操作 → API → prompt 組裝 → Claude → 後處理 → 回寫 DB／快取的流程。手繪拍照或 draw.io 都可以，重點是面試時能秒開。

## 案例 B：內容安全與審核管線（1.5h）

### 1. 問題
交友產品的內容風險：裸露圖片、假帳號、騷擾訊息、未成年。漏一個的代價是什麼？（下架、法遵、使用者流失）

### 2. 做法
- **圖片同步審核**：AWS Rekognition，同步的原因是什麼？延遲多少可接受？
- **影片非同步審核**：為什麼非同步？佇列怎麼設計？審核未完成時內容的狀態機是什麼（pending / approved / rejected）？
- **敏感詞攔截**：字典法還是模型？誤判怎麼處理？
- **真人臉部驗證**：活體檢測？和註冊流程怎麼接？
- **人審接口**：機器不確定時（信心分數落在灰帶）怎麼辦？有沒有人工複審佇列？

### 3. 結果
- 審核覆蓋率、平均審核延遲、誤判率（如果有記錄）
- 上架審查一次過 / 沒有因內容問題被下架
- 若沒有量化數據，就寫「上線至今零內容事故」這類可驗證的事實陳述

### 4. 一張圖
上傳 → 同步/非同步分流 → Rekognition → 信心分數分流（自動通過 / 自動拒絕 / 人審）→ 狀態機。

## 順帶處理：Staff 級影響力的素材（30 分鐘）

Cake 說你缺「可複用的方法論」。你其實有 —— 在云桐導入的 design review / code review / release checklist。

寫成第三份短文件（半頁即可）：

- **問題**：11 人團隊、多款遊戲產品、實作標準不一致
- **做法**：三個機制各自解決什麼問題？導入時遇到什麼阻力？怎麼讓人願意用？
- **結果**：沿用到幾款產品？缺陷率／回滾率有沒有變化？離職後還在用嗎？

這份不放履歷，是面試被問「你怎麼影響團隊」時的備彈。
