# Day 3 — AI 深度補強（4h）★ 本次衝刺的核心

**要解決的缺口**：Cake 唯一標為「工作經歷」層級的弱項 ——
> 「資料裡比較少看到您長期負責**模型評估、提示設計體系、資料標註策略或 AI 指標治理**這類更深的工作。」

**產出**：一份可展示的 AI 品質治理成果（eval set + 指標定義 + prompt 版本紀錄），以及履歷上三行新的、有東西撐的敘述。

---

## 為什麼這一天不能跳過

其他四天都是「把既有事實講得更好」。**只有這一天是真的長出新東西。**

而且這件事你可以在現職就做完 —— 你手上就有一個正在跑的 LLM 產品。這不是做作品集，是把你本來就該做的品質工作補齊並記錄下來。做完之後，這不再是「面試話術」，是你真的在負責的事。

---

## 任務 1：建一組 eval set（90 分鐘）

挑**一個**功能就好，建議「破冰話題生成」或「個人簡介生成」（輸出短、好評分）。

### 步驟

1. **蒐集 30–50 個真實輸入**
   從產品現有資料抽（注意去識別化）。要涵蓋：典型案例、邊緣案例（資料極少的使用者）、惡意輸入（試圖越獄的 prompt）。

2. **定義「好」的標準**（這是最有價值的部分）
   例如破冰話題：
   | 維度 | 定義 | 評分 |
   |------|------|------|
   | 相關性 | 是否用到雙方共同興趣 | 0–2 |
   | 安全性 | 是否涉及敏感／冒犯內容 | 0/1（硬性） |
   | 可回覆性 | 對方能不能自然接話（非是非題） | 0–2 |
   | 語言自然度 | 是否像真人會說的話 | 0–2 |

3. **人工標一遍當基準線**
   30 筆自己標，記錄總分與各維度分數。這就是 Cake 說的「資料標註策略」。

4. **寫成可重跑的腳本**
   一支 Node/TS script：讀 eval set → 打模型 → 存結果 → 產出分數表。
   加分項：用 LLM-as-judge 做自動評分，但**必須先驗證 judge 和你的人工標註一致率**（算一下 agreement，低於 80% 就別用）。

### 產出檔案
```
eval/
  dataset.jsonl        # 輸入 + 人工標註
  rubric.md            # 評分標準定義
  run-eval.ts          # 執行腳本
  results/2026-07-31.json
```

## 任務 2：prompt 版本管理（60 分鐘）

現在你的 prompt 大概散在程式碼裡。改成有版本、有紀錄。

**最小可行做法**（不要引入 LangSmith 這類重工具，一人團隊用不上）：

1. prompt 抽成獨立檔案／常數，加上版本號與變更日期
2. 開一份 `prompts/CHANGELOG.md`：每次改 prompt 記下 **改了什麼 / 為什麼改 / eval 分數變化**
3. 把 eval 跑成 CI 的一個 job（或至少一個 npm script），**改 prompt 前後各跑一次**

這三步做完，你就能在面試回答：

> 「改 prompt 前後我會跑一組 40 筆的 eval set，看相關性和可回覆性的分數變化。上次調整 system prompt 讓相關性從 1.4 升到 1.7，但安全性掉了一筆，所以我又補了一條約束。」

這句話的份量，跟「我用 Claude 做了破冰話題」差三個級距。

## 任務 3：定義三個 AI 產品指標（45 分鐘）

Cake 說的「AI 指標治理」就是這個。挑三個你現在**就能量測**的：

| 類型 | 指標範例 | 為什麼重要 |
|------|---------|-----------|
| 品質 | eval 平均分、人工複審拒絕率 | 模型輸出有沒有變差 |
| 使用 | AI 功能採用率、生成內容的採納率（使用者真的送出了嗎） | AI 有沒有被用 |
| 成本／效能 | 單次呼叫成本、P95 延遲、快取命中率 | 能不能規模化 |

**採納率**特別重要 —— 它是「AI 功能有沒有真的產生價值」最直接的證據，而且多數候選人講不出來。

把這三個指標接到現有的觀測（你履歷有 Sentry / Grafana / Kibana），做一個最小 dashboard 或每週手動記錄表都行。

## 任務 4：回寫履歷（45 分鐘）

Day 1 改過的 `work.json` 感覺銀航段落，加上第 7 條：

> **AI 品質治理**：建立 40 筆標註 eval set 與四維度評分標準（相關性／安全性／可回覆性／自然度），將 prompt 變更納入版本管理與迴歸驗證；追蹤生成內容採納率、單次呼叫成本與 P95 延遲，作為功能調整依據。

`whyme.json` 的「AI 產品整合」擴寫成：

> **AI 產品整合與品質治理**：運用 Claude 實作配對建議、聊天教練與破冰話題／個人簡介生成，並整合至產品流程；建立提示設計的版本管理與評估機制，以標註資料集與量化指標驗證輸出品質，而非僅憑人工抽查。

**注意**：這兩段只有在任務 1–3 真的做完之後才能寫上去。面試官會追問細節，寫了做不到就是反效果。
